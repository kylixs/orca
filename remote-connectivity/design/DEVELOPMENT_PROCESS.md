# 移动端功能开发流程规范

> **子代理协作**：主会话与子代理的派发/看护/回复/回收协议见 [parent-child-session-protocol.md](2026-11-13-cloud-dev-platform/parent-child-session-protocol.md)（2026-11-14 确立：一令一代理、三权分立、15 分钟预算、1 小时看护阈值、询问必写明回复方式）。

> 版本：1.0（2026-11-10）
> 适用：本仓库移动端多需求并行交付
> 原则：**每个门禁由独立子代理评审；不通过不进入下一阶段；所有结论有产物、有证据**

---

## 1. 角色

| 角色                               | 职责                                                                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **主会话（调度/管理 + 方案文档）** | 维护任务列表、设计/测试/任务拆分文档，拆分与分派任务、检查门禁、集成子代理产出、运行验收命令、向用户汇报；**不直接写功能代码** |
| 调研子代理                         | 只读梳理现状、文件路径、约束                                                                                                   |
| UI 原型子代理                      | 生成 UI 原型与关键状态，响应设计评审意见                                                                                       |
| 开发子代理                         | 按 `tasks.md` 实现代码与单元/组件测试，响应代码评审意见                                                                        |
| 设计/UI 评审子代理                 | 独立评审设计方案、测试方案、任务拆分、UI 原型                                                                                  |
| 代码评审子代理                     | 独立评审实现 diff、测试代码、兼容性与回归风险                                                                                  |
| 测试执行子代理                     | 运行自动化/真机测试，生成报告与证据                                                                                            |
| 测试评审子代理                     | 独立评审测试报告与覆盖度，执行探索性测试                                                                                       |
| **验收审计子代理（独立审计）**     | 对**用户提交的问题/需求交付项**做代码×证据×复跑三重核验；判定 PASS/REJECT/RETEST；不参与实现、只读、不得修改产品代码       |
| 用户                               | 需求确认、阻塞决策、最终验收                                                                                                   |

**执行分工**：

- 方案与计划文档（`design.md`、`test-plan.md`、`tasks.md`）由主会话维护；调研、UI 原型、开发、评审、测试等复杂任务分派给子代理。
- 同一时间并行的开发子代理应各自使用隔离 worktree，或分配互不重叠的文件；主会话负责合并与冲突处理。
- 子代理完成后返回产物路径与摘要，主会话必须打开产物核实，不能只看摘要。

**独立性要求**：评审子代理不得是产出该产物的代理；评审只读，发现问题写评审报告，由主会话或对应 UI/开发子代理修复后重新提交。**验收审计子代理同样不得参与该交付项的任何实现或测试编写**，审计过程只读（可运行测试），发现不达标一律回派重测/修复。

## 2. 产物目录

每个需求一个目录：

```text
remote-connectivity/design/<date>-<feature>/
  design.md                     # 设计方案
  test-plan.md                  # 测试方案
  tasks.md                      # 任务拆分与状态
  ui/                           # UI 原型（HTML/截图）
  reviews/
    design-review-01.md         # 设计与 UI 评审
    design-review-02.md         # 修订后复审（如有）
    code-review-01.md           # 代码评审
    test-review-01.md           # 测试与探索性测试评审
  test-reports/
    automated-test-report.md
    exploratory-test-report.md
    evidence/                   # 截图、录屏、日志、命令输出
```

所有评审结论必须落盘，不能只在对话里说“通过”。

## 3. 阶段与门禁

```text
G0 调研完成
  ↓
G1 设计方案 + 测试方案 + 任务拆分
  ↓
G2 UI 原型
  ↓
G3 独立设计/UI 评审通过（无 blocker/major）
  ↓
G4 开发完成（代码 + 单元/组件测试）
  ↓
G5 独立代码评审通过（无 blocker/major）
  ↓
G6 自动化测试 + 真机/模拟器验证 + 报告
  ↓
G7 独立测试评审通过 + 探索性测试完成（无 blocker/major）
  ↓
G8 修复、全量回归、最终验收
```

### G0 调研

- Explore 子代理输出：现有实现、文件路径、RPC、平台约束、差距。
- 主会话把调研结论引用到 design.md 的“现状”章节；复杂背景可让调研子代理补充事实。
- **出口条件**：三块需求（文件浏览、终端、HTML）的现状都已被调研并记录。

### G1 设计方案 + 测试方案 + 任务拆分

`design.md` 必须包含：

- 目标、非目标、用户流程
- 现状与差距（带文件路径）
- 方案（组件、状态、RPC、平台适配、边界情况、安全）
- 备选方案与取舍
- 验收标准

`test-plan.md` 必须包含：

- 单元、组件、集成、真机/模拟器、回归
- 测试数据（CJK/emoji/宽字符/折行/大文件/二进制/无权限等）
- 每条验收标准对应的用例编号
- 测试工具与报告生成方式

`tasks.md` 必须包含：

- 可独立执行的开发任务，标注文件/模块与依赖
- 每个任务的测试任务
- 风险与回滚点

**出口条件**：三份文档齐全，验收标准可测试。

### G2 UI 原型

- 关键界面至少覆盖：文件操作菜单、预览选区菜单、终端链接选择、中文选区手柄、HTML 打开方式菜单、代码/渲染切换。
- 原型放到 `ui/`，可为 HTML 或截图；标注交互状态（默认/长按/选中/禁用/无权限）。
- 原型不代替真实 UI，但必须能指导实现。

**出口条件**：每个需求至少一张主流程原型 + 关键状态。

### G3 独立设计/UI 评审

评审检查：

- 需求覆盖是否完整（逐条对照用户需求）
- 平台可行性（iOS/Android/Expo/WebView）
- 交互一致性、可发现性、误触风险
- 测试方案是否能证明验收标准
- 任务拆分是否有遗漏、依赖是否合理
- 安全/隐私/权限/大文件/离线等边界

评审报告格式：

```markdown
# 设计评审 01

结论：REJECTED / APPROVED_WITH_MINORS / APPROVED

## Findings

- [BLOCKER] ...
- [MAJOR] ...
- [MINOR] ...

## 建议修改

...
```

- 有 BLOCKER/MAJOR → 主会话（方案/计划文档）或 UI/开发子代理（原型/代码）修改 → 复审（新评审文件编号 +1）。
- 只有 MINOR → 可带条件通过，但必须在 tasks.md 记录处理决定。
- **出口条件**：评审结论为 APPROVED 或 APPROVED_WITH_MINORS，且无未处理 blocker/major。

### G4 开发

- 按 tasks.md 顺序实现；每个任务附单元/组件测试。
- 遵守 AGENTS.md / STYLEGUIDE.md；不得禁用 max-lines 等 lint 规则。
- 每个阶段跑 `pnpm tc`、`oxlint`、相关测试；结果写入报告。
- 涉及移动端原生能力（下载/分享/Intent）时必须做平台判断，不允许 iOS/Android 行为互相污染。

**出口条件**：任务全部完成；typecheck/lint/单元测试通过；无已知 blocker。

### G5 独立代码评审

- 评审 diff、测试代码、RPC/协议兼容、错误处理、边界、性能。
- 重点：大文件、二进制、权限、路径穿越、CJK/宽字符、跨平台、回归风险。
- 报告格式同上；BLOCKER/MAJOR 必须修复并复审。
- **出口条件**：APPROVED 或 APPROVED_WITH_MINORS。

### G6 自动化测试 + 真机验证

- 运行全部自动化测试；生成 `automated-test-report.md`。
- 真机/模拟器验证：
  - Android：`adb` + 模拟器或已配对手机；截图/录屏/日志。
  - iOS：`xcrun simctl`（如可用）。
  - 逐条执行 test-plan.md 的设备用例，记录实际结果。
- 报告必须包含：环境、构建号、命令、通过/失败数、失败详情、证据路径。

**出口条件**：所有 blocker 用例通过；失败项有明确原因和修复计划。

### G7 独立测试评审 + 探索性测试

- 测试评审子代理检查：覆盖度、断言质量、是否有“假通过”、是否覆盖 CJK/平台/边界、回归范围。
- 探索性测试：不看用例，按真实用户路径尝试破坏性操作（快速点击、旋转、杀进程、弱网、切换应用、大文件、特殊字符）。
- 报告写入 `test-reports/exploratory-test-report.md`；问题按 BLOCKER/MAJOR/MINOR 分类。
- **出口条件**：无未处理 blocker/major；探索性测试覆盖所有新功能及关键旧功能。

### G7b 独立验收审计（交付项级）

- **触发**：用户提交的问题/需求形成交付项批次后（每批交付声明完成后），主会话建立**审计计划**（`work-orders/uNNN-acceptance-audit-plan.md`）：逐项列「用户原话 → 实现提交哈希 → 证据目录 → 审计组」。
- **审计代理**：独立子代理（未参与该项实现/测试），按组分派；只读代码与证据，可自行复跑测试。
- **三重核验口径**：
  1. **代码**：实现与交付声明一致？有无静默降级/假接线/吞错？scope 与边界完整？
  2. **证据**：artifact 存在且非空；时间戳与提交顺序自洽；断言是「真断言」（数值/marker/负控），非摆设；FAIL 被诚实记录而非伪装绿。
  3. **复跑**：审计代理自跑关键单测/e2e（抽查），**不信代理转述**；`it.fails→it` 转正必须靠修产品而非放宽断言。
- **判定与回派**：每项 **PASS / REJECT（列具体缺陷）/ RETEST（证据不足须重测）**——REJECT/RETEST 由主会话立即回派修复令或重测令，闭环前不得向用户宣告该项完成。
- **报告**：`test-reports/uNNN-audit-{a,b,c}.md`；主会话汇总总评表（判定+缺陷计数）后向用户呈报。

### G8 修复与最终验收

- 修复评审/探索性问题，补回归用例。
- 全量回归：受影响的移动端模块 + 相关共享协议测试。
- 最终产物：更新 design/test-plan/tasks 状态、评审报告、测试报告、回归报告。
- **完成定义（DoD）**：
  - 所有验收标准有通过证据
  - 设计/代码/测试三份独立评审均通过
  - **交付项级独立验收审计 PASS（无未闭环 REJECT/RETEST）**
  - 自动化 + 真机验证通过
  - 无影响其它功能的回归
  - 文档与任务列表闭环

## 4. 测试要求

| 层级         | 工具                          | 要求                                             |
| ------------ | ----------------------------- | ------------------------------------------------ |
| 单元/组件    | Vitest（mobile）              | 新逻辑必须有测试；边界值、CJK/emoji/宽字符必测   |
| 类型/静态    | `pnpm tc`、`oxlint`           | 全绿，不允许新增禁用注释                         |
| WebView 文档 | mobile terminal document 测试 | 选区/链接/映射逻辑用 fake buffer 覆盖            |
| 真机/模拟器  | adb / xcrun simctl            | 至少 Android 模拟器；有条件加 iOS                |
| 探索性       | 人工 + 子代理                 | 覆盖误触、旋转、后台切换、弱网、大文件、特殊字符 |
| 回归         | 相关目录测试                  | 终端、文件预览、浏览器、会话创建等               |

测试报告中禁止只写“手工验证通过”；必须给出操作步骤、预期、实际、证据。

### 4.1 测试分级与并发控制（强制）

测试按阶段分级执行，**默认只跑最小集**；跑大范围必须显式声明并控制并发。

| 级别          | 触发时机                         | 范围                                                           |
| ------------- | -------------------------------- | -------------------------------------------------------------- |
| L1 最小测试   | 每次改动后、每次提交前           | **只跑被改动的文件及其直接邻居**（同目录测试、被改模块的测试） |
| L2 模块测试   | 一个模块完成、准备更新进度文档时 | 该模块涉及的所有测试文件 + 受影响的相邻模块                    |
| L3 里程碑测试 | 里程碑收口                       | 该里程碑涉及的所有模块测试，按模块分批                         |
| L4 全量验收   | 最终验收、发版前                 | 全仓测试，单独执行                                             |

命令形如：
`node node_modules/vitest/vitest.mjs run --config config/vitest.config.ts --maxWorkers=4 <file…>`

并发与负载规则：

- 测试命令**必须**带 `--maxWorkers`（默认 4），不得留空让 vitest 自行决定并发。
- **禁止并行运行两个大范围测试**；主会话与子代理也不得同时跑大范围测试。
- 跑 L3/L4 前先看负载（`uptime`）；1 分钟负载超过 CPU 核数一半时，先等待或降低 `--maxWorkers`。
- 大范围运行前声明范围与预计耗时；运行中发现负载过高立即终止，**不得把"部分跑完"的结果当结论**。
- 某用例在空闲机器上单独跑通过、只在全量并发时失败，先按负载导致的时序抖动记录，再复跑确认；既不能直接判为回归，也不能直接判为通过。
- `tsc` 与 `pnpm run check:code-quality:changed` 每轮都跑（不受分级限制），但避免与 L3/L4 同时执行。

## 5. 定时调度

- 每 10 分钟由定时任务触发一次跟进（分钟 3/13/23/33/43/53）。
- 每次触发必须：
  1. 读取本规范、任务列表、最新设计/评审/测试报告。
  2. 找到**下一个未完成且依赖已满足**的门禁。
  3. 只推进该门禁的一个步骤，避免重复劳动。
  4. 更新任务状态与产物文件。
  5. 汇报：当前门禁、完成项、阻塞、下一步。
- 定时任务不跳过评审门禁；评审未通过不得进入开发/测试。
- 若发现产物缺失或结论不一致，先补齐产物，再继续。

定时任务提示词固定引用本文件，避免流程漂移。

## 6. 报告模板

### 自动测试报告

```markdown
# 自动测试报告 <feature> <date>

环境：<OS/模拟器/设备/构建号>
命令：<完整命令>
结果：PASS <n> / FAIL <m>
失败项：<用例、错误、日志路径>
证据：<截图/日志路径>
```

### 评审报告

```markdown
# <design|code|test> 评审 <n>

范围：<文件/commit/报告>
结论：REJECTED | APPROVED_WITH_MINORS | APPROVED
Findings:

- [BLOCKER] <问题> — <影响> — <建议>
- [MAJOR] ...
- [MINOR] ...
```

## 7. 变更控制

- 需求变更：更新 design.md / test-plan.md / tasks.md，重新走 G3 评审。
- 协议变更：额外做 paired client/host 兼容性检查，并在代码评审中单列。
- 任何跳过门禁的情况必须由用户明确批准，并记录在 tasks.md。
