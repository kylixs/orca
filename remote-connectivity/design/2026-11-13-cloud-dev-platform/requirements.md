## 1. 背景与目标

公司研发环境分散在办公网与内网机房，开发者需要在自己的电脑上通过 AI 编程工具（Claude Code 等）连接远端开发机完成开发。现状问题是：每台开发机各自配对、各自授权、无人审计，代码与凭证散落在个人设备上；跨网段访问依赖临时隧道，稳定性与合规性都无法保证。

本项目建设一个公司内部的**云端开发平台**：以 Orca 为客户端与运行时基础，在其上增加企业身份、项目目录、主机注册、地址发现与审计能力。平台不承载业务流量。

### 1.1 建设目标

| 编号 | 目标                                                                                                                                                                                                           | 衡量方式                                                                            |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| G1   | 员工用公司域账号一处登录，进入工作台看到自己有权限的项目                                                                                                                                                       | 登录到项目列表 ≤ 2 次点击                                                           |
| G2   | 打开项目即获得与本地 Orca 一致的开发体验（终端、Claude、编辑器、文件浏览）                                                                                                                                     | 功能清单对齐，交互无额外学习成本                                                    |
| G3   | 开发机统一注册，客户端直连优先、中继兜底，办公网与外网用户都能稳定连接                                                                                                                                         | 连接成功率 ≥ 99%，直连 P95 ≤ 2s，中继 P95 ≤ 3s                                      |
| G4   | 受管客户端内禁止专用导出入口；主机拒绝专用下载 RPC；所有导出尝试可审计                                                                                                                                         | 受管客户端导出入口拦截 100%，主机拒绝率 100%，审计可追溯（内容读取不受阻断，见 C1） |
| G5   | 平台可运维：主机、项目、权限、审计集中管理                                                                                                                                                                     | 管理员无需登录开发机即可完成日常运维                                                |
| G6   | **零参数使用（用户 2026-11-14 确立为项目目标）**：终端用户**不输入任何参数、环境变量或配置文件**——安装后启动即见登录页，地址默认/记忆预填，一切配置经界面完成；开发模式与测试可用 env 加速，但用户路径永不依赖 | 衡量：全新机器安装 → 启动 → 登录成功，全程 0 次终端命令、0 个环境变量（G1 的前置）  |

### 1.2 设计原则

1. **复用优先**：客户端与运行时基于 Orca 上游，不另起炉灶；企业能力以补丁层形式叠加。
2. **平台只做注册与授权**：平台是注册中心 + 认证授权中心，签发地址与凭证；业务流量由客户端与开发机直接建立，平台不参与、不转接、不解密。
3. **端到端加密不被削弱**：客户端与开发机之间保持 Orca E2EE；中继只做 TCP 转发。
4. **默认拒绝**：未授权项目不可见，未授权操作不可用，下载默认禁止。
5. **可回退**：平台故障不影响已有会话；中继故障不影响直连；新会话降级而非整体不可用。
6. **零参数原则**：任何需要用户输入参数/环境变量才能用的设计都视为缺陷；env 与配置文件仅供运维部署与企业分发预设，用户界面是唯一运行时配置入口。
7. **云端是附加渠道（用户 2026-11-14 确立）**：客户端完整保留 Orca 原生能力——添加本地项目、配对其他 Orca 远程主机项目；云端开发平台只是其中一个**特殊渠道**（登录后以额外项目源呈现），与原生项目并存、互不排斥；任何云端功能不得移除或遮蔽原生入口。

## 2. 角色与术语

### 2.1 角色

| 角色                         | 说明                                     | 主要诉求                                     |
| ---------------------------- | ---------------------------------------- | -------------------------------------------- |
| 开发者（Developer）          | 使用平台进行日常开发                     | 快速登录、快速打开项目、稳定的终端与 AI 会话 |
| 项目负责人（Project Owner）  | 对某个项目的成员与策略负责               | 管理项目成员、调整项目级权限                 |
| 平台管理员（Platform Admin） | 负责主机、项目登记、全局策略             | 注册/下线主机、创建项目、配置下载策略        |
| 审计员（Auditor）            | 安全与合规角色，只读                     | 查询审计日志、导出证据（需审批）             |
| 开发机（Dev Host）           | 运行 Orca Runtime 的受管主机，非人类角色 | 注册、心跳、执行工作区与终端                 |

登录准入由 LDAP 分组门槛控制（ORCA_CLOUD_LDAP_REQUIRED_GROUP，加入准入组才能登录）；角色（普通/审计/管理员）由平台内用户管理页管理，与 LDAP 组无关。

### 2.2 术语

| 术语                              | 定义                                                                                          |
| --------------------------------- | --------------------------------------------------------------------------------------------- |
| 开发平台 / 平台                   | 本文所述系统整体，包含平台后端（注册 + 认证授权）、Web 管理台、中继、开发机 Agent、桌面客户端 |
| Orca Runtime                      | 跑在开发机上的无头 Orca（`orca serve` / orcad），负责 PTY、Agent、文件、Git                   |
| 项目（Project）                   | 一台已注册开发机上的一个受管代码目录（git 仓库或 worktree），是权限与审计的最小单位           |
| 工作区（Workspace）               | 项目下按分支/任务创建的具体工作目录，对应 Orca 的 worktree                                    |
| 中继（Relay）                     | 部署在 DMZ 的纯 TCP 转发组件，仅在客户端无法直连开发机时提供通路                              |
| 直连（Direct）                    | 客户端直接到达开发机 `6768` 端口的路径（办公网/VPN 内）                                       |
| 连接凭证（Connection Credential） | 平台签发的短时效凭证，声明某用户在某项目上可连接某主机；由开发机验签                          |
| 托管项目（Managed Project）       | 由平台登记并强制执行策略的项目；未登记目录不可通过平台打开                                    |

### 2.3 平台形态

平台本身是一个 **Web 前后端分离系统**：

```
┌───────────────────────────┐   ┌───────────────────────────┐
│ 平台 Web 前端（SPA）        │   │ Orca Cloud 桌面客户端       │
│ 工作台 / 项目 / 主机 / 权限  │   │ 工作台 · 项目视图 · 选路    │
│ 审计 / 平台设置（管控面）    │   └─────────────┬─────────────┘
└─────────────┬─────────────┘                 │
              │ REST/JSON                        │ ① REST（登录/项目/地址/凭证）
              ▼                                  ▼
        ┌──────────────────────────────────────────────────┐
        │ 平台后端 API = 注册中心 + 认证授权                  │
        │ 身份 · 项目 · 主机注册 · 证书签发 · 策略 · 审计      │
        └──────────────────────────────────────────────────┘

  桌面客户端 ──② 直连 wss://devhost:6768──────────────► 开发机 Runtime
            └─③ 直连不通：wss://relay ──TCP 转发──────► 开发机 Runtime
            （②③ 为业务数据面，不经过平台）
```

| 规则           | 说明                                                                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 前后端分离     | Web 前端为独立 SPA 工程，只通过版本化 REST API 访问后端；前端可独立构建、发布、回滚                                                           |
| 平台定位       | **注册中心 + 认证授权中心**：维护主机/项目注册信息，校验身份与权限，下发开发机地址（直连 + 中继）与短期连接凭证                               |
| 数据面独立     | 客户端拿到地址与凭证后**自行建立链路**；直连优先，不通再经中继；平台不代理、不转接业务流量                                                    |
| 中继定位       | 纯网络转发（TCP），打通办公网与内网；不解析 Orca 协议、不解密、不参与授权判定                                                                 |
| 管控面权限     | 主机、项目授权、下载策略、审计、平台设置属于管控面，**必须显式授予平台管理权限才能查看**；无权限时导航不出现，直接访问接口返回 403 并记录审计 |
| 同一身份体系   | Web 前端与桌面客户端共用 LDAP 登录、会话令牌、RBAC 与项目 ACL                                                                                 |
| 桌面客户端定位 | 承载开发体验（工作台-项目列表-项目视图）与选路；不提供主机注册、成员授权、审计等管控功能                                                      |

## 3. 用户旅程

### J1 首次使用

1. 员工从公司软件中心安装「Orca Cloud」客户端。
2. 打开客户端看到登录页，输入域账号与密码。
3. 平台经 LDAPS 校验成功并核对准入组，签发会话；LDAP 组用于准入与资源授权，不映射平台角色。
4. 进入工作台，看到自己有权限的项目卡片与列表。
5. 选择项目 → 点击「打开」→ 客户端展示选路进度 → 进入项目视图。
6. 在终端中运行 `claude`，开始与 AI 协作。

### J2 日常使用

1. 客户端保持登录态，启动后直接进入工作台（令牌有效时）。
2. 项目视图顶部显示当前线路（直连/中继）、延迟、主机名。
3. 工作区列表可切分支、新建工作区；文件浏览器只读浏览。
4. 尝试下载文件时被拦截，提示项目策略并引导申请（二期）。

### J3 管理员注册主机

1. 管理员在管理台「主机」页点击「注册主机」，生成一次性令牌（24 小时有效）。
2. 在目标开发机执行平台给出的安装命令。
3. Agent 注册成功，上报指纹、版本、监听地址、网络位置。
4. 平台记录该主机的直连地址与中继地址；客户端连接时按序探测，直连不通再走中继。
5. 管理员创建项目并绑定主机、路径、可见组。

### J4 连接故障

1. 开发者打开项目，直连探测超时，自动回落中继。
2. 若中继也不可达，展示错误面板：错误码、分步诊断、重试入口。
3. 开发者可复制诊断信息提交给管理员。

#### FR-9.10 主机级授权语义（全权 / 只读两级）

| 编号    | 需求                                                                                                             | 优先级 |
| ------- | ---------------------------------------------------------------------------------------------------------------- | ------ |
| FR-9.10 | 主机授权只设**全权**与**只读**两级；两级分别推导项目可见性、创建能力与项目内操作上限，管理台不暴露第三种有效级别 | P0     |

**语义定义**

- **主机全权**（底层 `provision + maintain + view` 三位）：持有者可见该主机**全部非归档项目**（不要求任何项目级授权），可在该主机创建/登记项目，可管理主机维护状态，并在该主机全部项目内拥有全部项目操作位（`open`、`terminal`、`agent`、`file:read`、`file:write`、`browser`）。`download` 不在「全权」推导范围内，始终受 FR-7 下载策略独立约束。
- **主机只读**（底层仅 `view`）：持有者可见并可打开该主机全部非归档项目，但项目内有效权限上限为 `open + file:read`；不得创建/登记项目（无 `provision`）、不得维护主机（无 `maintain`）、不得编辑文件、不得开终端/Agent、不得使用浏览器、不得下载——即使项目级授权显式包含这些位。
- **混合位降级**：管理台只写入上述两级组合；历史或直写产生的混合位按最小权限降级——缺 `view` 不推导项目可见性，缺 `provision` 不可创建，缺 `maintain` 不可维护，`provision`/`maintain` 不授予项目内读写权限。
- **平台管理员旁路**：持有平台管理角色的账号可管理主机与授权，不受自身主机只读授权约束；旁路操作与授权变更均留审计（FR-9.7）。

**用户故事**

- **平台管理员（admin）**：我在主机权限抽屉里只需选择「全权」或「只读」就能表达授权意图，不必逐项目勾选；给同事开全权后，该主机后续新增项目自动对他可见，不会漏授权。
- **开发者（zhangsan）**：我被授予某主机全权后，能直接看到并在该主机上创建/添加项目，进入任意项目即可使用终端、Agent 与文件编辑，无需项目负责人逐个项目加白。
- **受限开发者（lisi）**：我只有某主机只读授权时，可以打开该主机上的项目查看代码，但新建项目、终端、Agent、编辑保存和下载都不可用；界面明确提示这是主机只读策略，而不是逐个操作报错。

**验收标准（Given/When/Then）**

- **AC-33 主机全权：全项目可见 + 全操作位**
  - Given 管理员对主机 H 授予 zhangsan「主机全权」，H 上存在项目 P、Q，且 zhangsan 无任何项目级授权
  - When zhangsan 登录并刷新工作台，打开 P
  - Then 工作台列出 P 与 Q；P 内终端、Agent、文件读写、浏览器可用；下载仍按 FR-7 策略判定（默认禁止）
- **AC-34 主机只读：项目内操作上限**
  - Given 管理员对主机 H 授予 lisi「主机只读」，项目 P 另有一条给 lisi 的项目授权，包含 `terminal`、`file:write`
  - When lisi 打开 P 并尝试开终端、保存文件、使用浏览器、下载
  - Then 四项均被拒绝（宿主 RPC 权限错误或前端入口禁用），审计记录主机只读上限；文件浏览与预览正常
- **AC-35 主机只读：不可创建/登记项目**
  - Given lisi 仅有主机 H 的只读授权，H 已声明 `projectsRoot`
  - When lisi 打开「新建项目」或直接调用创建接口并指定 H
  - Then H 不出现在可创建主机列表；直接调用返回 403（`HOST_PROVISION_FORBIDDEN`）并写 denied 审计

#### FR-9.11 主机授权与项目授权的关系（继承 / 上限 / 不扩大）

| 编号    | 需求                                                                                                                                                                                                                                                                                                                                                                                                                                                  | 优先级 |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| FR-9.11 | 主机授权与项目授权按三原则合成，既有项目级权限位语义不变：①**继承**——主机授权对当前及未来该主机全部项目生效；全权推导全部项目操作位，只读推导 `open + file:read`。②**上限**——主机只读是该主体在该主机所有项目内的权限上限，项目级授权不得突破；无主机授权时项目授权仅在该项目内生效。③**不扩大**——项目级授权永不扩大为主机级：不产生其他项目可见性、不产生创建/登记能力、不产生主机维护权限；仅有项目授权的用户看不到同主机未授权项目，也不能创建项目 | P0     |

| 主体在该主机上的授权                      | 可见项目             | 可创建/登记项目 | 项目内有效权限                            |
| ----------------------------------------- | -------------------- | --------------- | ----------------------------------------- |
| 主机全权（`provision + maintain + view`） | 该主机全部非归档项目 | 是              | 全部项目操作位（`download` 受 FR-7 约束） |
| 主机只读（仅 `view`）                     | 该主机全部非归档项目 | 否              | 仅 `open + file:read`（项目授权不得突破） |
| 无主机授权、有项目授权                    | 仅被显式授权的项目   | 否              | 项目授权位（受 FR-7 与主机边界约束）      |

**用户故事**

- **平台管理员（admin）**：我把某人设为某主机只读后，即使项目负责人额外给了他终端权限，他在该项目里也不会获得终端——上界由主机授权控制；我只授权单个项目时，权限也不会意外扩散到整台主机。
- **开发者（zhangsan）**：作为项目负责人，我给 lisi 授了项目 P 的 `terminal`，平台提示该授权因 lisi 的主机只读上限而不生效；我理解需由管理员提升主机授权，而不是重复加项目权限。
- **受限开发者（lisi）**：我只被授权项目 P 时，只看到 P、看不到同主机的 Q，也不能新建项目；我的权限不会因为访问过某台主机而扩大。

**验收标准（Given/When/Then）**

- **AC-36 项目授权不扩大到主机级**
  - Given lisi 仅在主机 H 的项目 P 上拥有 `open + file:read`，对 H 无任何主机授权
  - When lisi 登录工作台，搜索并按 ID 访问 H 上的未授权项目 Q，同时尝试在 H 创建项目
  - Then 工作台仅显示 P；Q 的搜索无结果、按 ID 返回 404；H 不出现在可创建主机列表，创建接口返回 403 并写审计
- **AC-37 主机全权对新项目继承**
  - Given zhangsan 已持有主机 H 的主机全权
  - When 管理员或他人随后在 H 上登记新项目 Q（未显式授权 zhangsan）
  - Then zhangsan 刷新工作台即见 Q 并可打开；无需新增项目级授权
- **AC-38 主机授权降级传播**
  - Given lisi 当前持有主机 H 全权且已打开项目 P
  - When 管理员把 lisi 在 H 上降级为只读
  - Then 在主机与平台心跳正常的前提下 60 秒内生效：P 内终端/写入被拒，已建立连接按 FR-1.7 断开或降权，审计记录变更

#### FR-9.12 文件下载 server 侧拦截（两期交付）

| 编号    | 需求                                                                                                                                                                                                                                                                                                                                                       | 优先级                 |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| FR-9.12 | 文件下载的终态防线在 **orca server（宿主）侧**：禁止策略下由宿主在 RPC 层拒绝下载与导出。考虑工作量进行分期——**一期**先做 orca web / 客户端 web / 管理台详情页的前端拦截与审计（体验层，明确**不是安全边界**）；**二期**补齐宿主硬拦，前端拦截降级为体验优化。分期期间须登记「绕过前端直连 RPC 仍可下载」的已知缺口，不得宣称已满足 G4/FR-7.3 的 100% 拒绝 | P0（一期）/ P1（二期） |

**分期定义**

- **一期（前端拦截）**：在 orca web、桌面客户端内嵌 web、管理台项目详情页，当项目/全局下载策略为「禁止」时，隐藏或禁用下载、导出、拖拽到本地、浏览器「另存为」相关入口；用户触发时给出原因与下一步（申请，二期可用），并写 `download_blocked` 审计。前端判断不得被当作唯一防线。
- **二期（宿主硬拦）**：宿主（orca server）在 RPC 层对 `files.download`、`files.downloadFolder`、`terminal.exportArtifact`、`browser.download`、`browser.savePage` 等专用下载/导出方法按凭证权限与下载策略拒绝，不受客户端形态影响；保留 FR-7.3 的「任意文件读取不阻断，限速 + 审计」语义。拒绝审计包含 user、project、path、size、method、result、traceId。

**用户故事**

- **平台管理员（admin）**：我能清楚看到下载策略在前端与宿主两端的分期生效状态，并知道一期不是安全边界；向审计解释拦截覆盖范围时不含糊。
- **开发者（zhangsan）**：我在 orca web 或客户端点击下载、导出、拖拽时被立即拦截并看到原因，不会误以为平台允许而反复尝试。
- **受限开发者（lisi）**：我只有只读或受限权限时，任何下载/导出入口都不可见；即使我绕过前端直接请求，二期也会被宿主拒绝。

**验收标准（Given/When/Then）**

- **AC-39 一期前端拦截与缺口登记**
  - Given 一期部署，全局或项目下载策略为「禁止」
  - When 用户在 orca web / 客户端 web / 管理台详情页点击下载、导出、拖拽或浏览器另存
  - Then 入口不可见或动作被前端拦截，提示原因并写 `download_blocked` 审计；「直接 RPC 仍可能成功」作为已知缺口登记，不宣称安全边界已成立
- **AC-40 二期宿主硬拦**
  - Given 二期部署，全局或项目下载策略为「禁止」
  - When 用户通过任意客户端形态或裸 WebSocket 调用 `files.download`、`files.downloadFolder`、`terminal.exportArtifact`、`browser.download`
  - Then 宿主在 RPC 层拒绝并写审计（含 user、project、path、size、method、result、traceId）；前端拦截仅作体验层，不再是唯一防线

## 5. 非功能需求

### 5.1 性能

| 指标                               | 目标                         |
| ---------------------------------- | ---------------------------- |
| 登录（LDAP 校验后到工作台可交互）  | P95 ≤ 1.5s                   |
| 工作台项目列表加载                 | P95 ≤ 500ms（≤ 200 项目）    |
| 连接建立（连接凭证到工作区可交互） | 直连 P95 ≤ 2s；中继 P95 ≤ 3s |
| 终端输入回显（同城网络）           | P95 ≤ 120ms                  |
| 文件目录读取（1000 项）            | P95 ≤ 400ms                  |
| 审计查询（31 天窗口）              | P95 ≤ 2s                     |

### 5.2 可用性与容量

| 项           | 目标                                                 |
| ------------ | ---------------------------------------------------- |
| 控制面可用性 | 99.9%（月度）                                        |
| 中继可用性   | 99.9%                                                |
| 规模         | 500 开发者、200 台开发机、峰值 300 并发会话          |
| 中继容量     | 单节点 2000 并发 TCP，2Gbps；至少 2 节点             |
| 故障恢复     | 单节点故障不影响新会话建立；已断会话由客户端自动重连 |

### 5.3 安全

| 项         | 要求                                                                                                                                                             |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 传输       | 公网/办公网 TLS 1.2+（优先 1.3）；**携带连接凭证的 WSS 升级必须 TLS（内网亦然）**；中继按 SNI 透传                                                               |
| 端到端     | 客户端与开发机之间保持 Orca E2EE（nacl.box）；中继与网络链路不可解密。平台是主机公钥的分发者（信任根），客户端首次连接固定指纹后，平台无法在不被发现的情况下替换 |
| 凭证       | 域密码不落库、不落日志；令牌加密存储；签名密钥 90 天轮换                                                                                                         |
| 授权       | 默认拒绝；最小权限；权限变更在心跳正常前提下 60 秒内传播；未登记的新 RPC 方法默认拒绝                                                                            |
| 注入与穿越 | 路径穿越、命令注入、SSRF 均需防护并测试                                                                                                                          |
| 审计       | 所有敏感操作可追溯；日志完整性校验                                                                                                                               |
| 供应链     | 依赖锁定、构建可复现、镜像签名                                                                                                                                   |

### 5.4 合规与数据

- 不记录终端内容、文件内容、AI 对话内容。
- 审计日志保留 180 天，归档存储加密。
- 用户信息仅同步必要字段（账号、姓名、部门、邮箱、组），不做二次画像。

### 5.5 可维护性

- 客户端基于 Orca 上游同步，企业补丁独立成目录，升级冲突可控。
- 所有服务提供健康检查、指标、结构化日志。
- 配置变更无需重启（策略类）；二进制升级支持灰度与回滚，回滚 ≤ 30 分钟。

### 5.6 架构形态

| 项         | 要求                                                                                         |
| ---------- | -------------------------------------------------------------------------------------------- |
| 前后端分离 | Web 前端为独立 SPA，通过版本化 REST API 访问后端；静态资源与 API 可分别部署                  |
| 管控面隔离 | 管控面接口在路由层统一鉴权，权限不足返回 403；前端隐藏入口不作为安全边界                     |
| API 契约   | 使用 OpenAPI 描述，前后端以契约为准；破坏性变更需版本升级与灰度                              |
| 会话       | Web 前端使用 HttpOnly + Secure + SameSite Cookie 承载会话；桌面客户端使用内存 + 系统安全存储 |

### 5.7 兼容性

- 客户端：macOS 12+、Windows 10 1909+、Ubuntu 22.04+（可选）。
- 开发机：Ubuntu 22.04/24.04、macOS、Windows；CentOS 7 通过容器运行。
- 协议：Orca 协议 v3，最低客户端协议 v2；低于最低版本拒绝连接。
