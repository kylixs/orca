# 父子会话沟通机制（主会话 ↔ 子代理协议）

> 版本：1（2026-11-14，用户指令确立）
> 适用：云端开发平台所有工作令的派发、跟催、回收；主会话=编排调度与快速检测，子代理=开发/测试/审计执行。

## 1. 角色与通道

| 角色         | 通道                                                | 职责                                                                                 |
| ------------ | --------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 主会话（父） | Agent 派发 / SendMessage 催办与追问 / Cron 周期盘点 | 拆解任务、派发、看护、核验收口、更新 PROGRESS 与台账                                 |
| 子代理（子） | 完成时自动回报（任务通知） / SendMessage 回复 main  | 执行单一任务；**被询问时必须用 SendMessage 回复 main**——直接文本输出对后台任务无感知 |

**核心规则：父会话向子代理提问时，消息里必须写明回复方式**（「请用 SendMessage 回复 main」或「结束任务让完成通知带回结果」），否则子代理的直接输出父会话无感知。

## 2. 派发规范

1. **一令一代理**：每个工作令（或细粒度任务）派一个全新代理；令内规格是唯一事实源（work-orders 文件）。
2. **两级审计梯（2026-11-16 用户指令合并原三权分立审计）**：实现代理 → 测试代理 → **审计梯**——①**令级审计**（原第三环，现降为**高风险令可选**：宿主安全边界/持久化/并发类才附加）；②**验收审计（每批必做，见 §3g）**。问题由主会话回派实现/测试代理；两级审计与实现/测试同样独立（不得参与该项实现/测试编写），只读+可复跑，不达标回派重测。原审计实践（U68 变异复现/LGAA 八项核查/W12b2/U46 批量/W9a-W9b）归入本体系。）
3. **20 分钟控制线（2026-11-14 用户修订，原 15 分钟目标）**：预估超时必须继续拆分；复杂令先派设计代理出方案，主会话确认再派实现。
4. **隔离**：主工作树有并发在途改动时，验证/旅程类代理用 `git worktree --detach <commit>` 隔离构建运行；实现代理用「逐文件 add + 提交前 `git diff --cached --stat` 核对=预期文件」。
5. **技术方案必备节：AC→测试用例映射表**（2026-11-15 复盘固化——验收代理按映射逐条执行的基础设施）。
6. **必带交付要求**：证据目录（`cloud-platform/evidence/<task>/`）、提交消息、测试输出（pass/fail 数）、超范围即停；**修复令另须留存 implementation.diff**（并发回退时的自恢复依据，2026-11-15 复盘固化）。
7. **pathspec 前核验（2026-11-16 复盘固化）**：主会话/代理对**非本会话编写**的文件做 pathspec 提交前，必看 `git diff --stat` 核对改动范围——外部写手会对工作树做格式化乃至截断（原型/设计文档/方法文档三例），不可假设「只有我刚改的一行」。
8. **诊断令词纪律（2026-11-16 固化）**：诊断/排查类令词只给**用户可观测现象与期望**，不得预设实现文件/类名——预设会牵引代理走向错误方向（U96 判例：任务词点名工作区组件后方向偏差，重派为「仅现象+自主功能发现」后恢复）。需要范围约束时用功能语言（如「两种工作区形态」）而非代码符号。
9. **设计交付形态（2026-11-16 复盘固化——U67/LDAP 两次实证）**：设计文档必含「终审项（T 编号）+开放问题（Q 编号）」清单与文末「主会话审定节」；独立评审清单含编号引用一致性检查；审定+评审双通过前不派实现令。
11. **诊断声明必须被设计复核（2026-11-16 13:05 复盘固化——U96 Q2 判例）**：设计代理须逐条复核诊断的关键代码声明（"已/未实现"类断言），不一致处显式标注；主会话审定包含对诊断结论的交叉核对。站���断言深度同源纪律：验收站点须对应用户可感知状态做深度断言（U91 restart 站点判例——站点绿不等于恢复内容正确）。
10. **构建产物隔离（2026-11-16 固化——U103 判例）**：验证/旅程类构建**禁止在主工作树原地重建 `out/`**——持久环境（~/orca-local-env 宿主）正伺服主仓 `out/`，构建替换会造成在线客户端「旧 index 引用已删 chunk」类故障（U103：刷新停留登录界面）；构建一律在快照目录（git archive/worktree）内进行；若确需主树构建，构建后必须立即 reseed 持久环境对齐（资产与宿主内存同版本）。
11. **台账现状复核（2026-11-16 14:05 固化——U101 判例）**：修复令执行前必须复核台账声称的缺陷现状；发现过时（已修/本就绿）时更正台账并在交付中声明，不得照旧修。测试令若因构建/环境受限无法执行，必须在交付中显式声明「执行待办+触发条件」，主会话跟进闭环。
12. **进程清理禁令（2026-11-16 复盘固化——U88 判例）**：代理清理进程**禁止宽域 `pkill`/`killall`**，尤其禁止按源码路径（如 `pkill -9 -f "apps/api/src/server.ts"`）、通用 node/bun 模式或端口号 pattern 扫杀——同机持久环境常以相同源码路径/端口启动，会被一并误杀。只允许：①kill **自己 spawn 的子进程 PID**（记录 PID 后逐个发信号）；②按**本次运行特有的唯一临时标识**（如本次专属临时目录、随机 marker）匹配。仓库 harness 即此范式（`cloud-platform/test/e2e/harness.ts` 以 `spawned` PID 注册表精确 SIGTERM/SIGKILL），手工清理须照办。

## 2b. 并行模式（用户 2026-11-14 指令：不要串行开发，单独完整链路验收，发现即修不堵塞）

1. **开发令派发不再以「前一令测试/审计通过」为前置**：实现落地即放行下一开发令（同通道后续令与跨通道均可）；文件域不相交仍是硬约束（防工作树碰撞与提交卷入）。
2. **审计梯保持但并行化**：独立测试与审计（令级可选/交付项级必做）与后续开发**同时**跑，不再作为闸门串联；发现问题回派修复，修复本身也是开发令。
3. **完整链路验收=批量+异步**（用户 2026-11-14 追加指令）：不逐令逐波验收——积批（多个开发令落地或定时）后由专职验收代理对**当时 HEAD** 跑全链（双线黄金旅程 chain-smoke + 管理员链），占用一个普通槽位与开发并行；结论异步回流，**红项批量进修复队列**，绝不等待验收结果才派下一批开发。
4. **双绿仍是终局门禁**：向用户汇报「全部完成，等待人工验收」之前，双线黄金旅程必须全绿。
5. 并发上限 4 不变（真栈套件 CPU 争用会互相拖慢并致时序测试抖动）；空槽即时回填，不让槽位等待。

## 3. 看护（看消息时间，不看钟表）

1. **正常推进（未空闲/未堵塞）→ 不打扰**：以「最后消息/证据目录最新文件时间」判断；刚回报过状态或证据在增长的代理一律不催。
2. **超过 1 小时无最后消息 → SendMessage 了解**，且**必须写明回复方式**（见 §1）。
3. **确认卡死（无证据推进 + 询问无响应）→ TaskStop**，按剩余范围重派新代理（附前序遗留 diff 审阅指引，能续用则续用）。
4. **反例存档**：对 W9a 的过早催办（其正按自己节奏收尾且已主动回报）——催办前先看它最近是否已主动回报。
5. **环境体检（2026-11-16 复盘固化）**：看护轮含持久环境面检查——四进程存活+关键端点 HTTP 探针；异常即用幂等 reseed 一键恢复（U77 后脚本自愈闭环），平台静默掉线判例（05:05 复盘）不入阻塞、不惊扰用户。
6. **状态读数优先级（2026-11-16 复盘固化）**：证据文件 > git log > 台账行 > 会话记忆/摘要——台账行与文档 header 滞后是常态（U66 行滞后 APPROVED、W12 header 滞后已落地两例），任何派发/回收动作前按证据文件与 git log 核验当前态。

## 3a. 探索证据留存纪律（2026-11-15 用户指令）

**基线证据不可变（2026-11-16 审计 B D2 固化）**：基线/对照数据（before 数值、修复前 artifact）必须复制到只读子目录归档，测试运行不得覆盖；报告引用归档副本路径。

探索性测试的**证据/截图保留在磁盘但不随 git 提交**：findings JSON、截图、运行日志统一落 `cloud-platform/evidence/<轮次>/`（该目录在 .gitignore 中）；**可复用的是路径清单与脚本**（入库，见 §3b），不可复用的是一次性证据（留盘不入库）。两类产物严格分离。

## 3b. 探索路径复用（2026-11-15 用户指令）

探索性测试的**路径本身是资产**：每轮探索的页面/控件/API/链路操作序列必须整理为结构化路径清单（条目=「入口→步骤→检查点」，可附可执行脚本）**入库** `cloud-platform/scripts/exploratory-<轮次>/`，与 findings（evidence，gitignored）分离。后续回归/修正探索直接按路径清单重放，发现的修复以新用例追加进清单——路径清单持续演进，不重写。

## 3c. 小时级测试复盘机制（2026-11-15 用户指令，两次补充）

- **兜底（2026-11-16 复盘固化）**：整点独立复盘 cron 未触发时，主会话进度轮即行补执行（标记「补执行」），避免漏档。

**每 1 小时对测试工具及方法做一次复盘**：①收集本时段出现的问题——**四类**：（a）工具本身问题（假红/伪绿/时序抖动/环境破坏/脚本缺陷）；（b）**测试遗漏**（应测未测：路径清单缺的分支/交互/数据组合/身份形态、断言覆盖不到的输出面）；（c）**错判**（把对的判错=假红已含，把错的判对=漏判、严重级定错、根因判错、修复验证不充分即判绿、探索 findings 分级失准）；（d）方法缺口（探索手法单一/边界库未用/原型对照未做）。②调研解决办法（查根因、查工具文档、对照既有先例）；③**实验改进**（小步试验新方法/参数/工具形态，验证有效才固化为流程或脚本/路径清单条目）；④度量追踪（测试效率=单轮时长、覆盖率=路径清单与断言密度、准确率=假红率+漏判率+分级准确率）。复盘产出**单独记录**到 `cloud-platform/test-retrospective-log.md`（不混 PROGRESS——2026-11-15 用户指令）；固化项更新协议/脚本/路径清单。

## 3d. 子代理模型配置（2026-11-15 用户指令）

子代理统一使用 **glm-5.3-flash[1m]** 模型（随会话默认；派发时不传 model 参数即继承）。模型不可用（400/402）时按事故预案换可用模型续派，恢复的代理若复现模型错误立即以继承模型重派。

## 3e. 提交粒度纪律（2026-11-16 用户指令修订）

小修改**不自动逐笔提交**——按**功能粒度**归并提交：同一功能/修复的完成态一起提交（中途修改在工作树保留，代理「完成即提交」含义=功能完成态，非每次文件保存）；跨功能完成态可分别提交但不得拆碎；文档/设计类按主题归并。事故 8 的 --no-verify+pathspec 纪律不变。

## 3f. 并发调度下限（2026-11-16 用户指令）

每轮跟进时**活跃并发 <3 即须立即安排新任务**（从队列/P2 挂账/路径清单演进/探索扩面中取最优先者派发），不让槽位空转；资源争用（真栈套件 CPU）是唯一允许 <3 的例外，且须在汇报中说明。并发上限维持 6（真栈套件并行时按 CPU 回撤）。

## 3g. 独立验收审计（2026-11-16 用户指令固化——U111 实践）

1. **触发**：每批用户问题/需求交付声明完成后，主会话先建**审计计划**（`work-orders/uNNN-acceptance-audit-plan.md`）：逐项「用户原话 → 实现提交哈希 → 证据目录 → 审计组」；未完成/仅原型项标注「暂不审」。
2. **独立性**：审计代理不得参与该项任何实现/测试编写；只读代码与证据，可自行复跑测试。
3. **三重核验**：代码（实现 vs 声明/静默降级/scope 边界）· 证据（存在性/时间戳自洽/断言真实性/负控/FAIL 诚实记录）· 复跑（自跑关键套件，不信转述；`it.fails→it` 转正须靠修产品而非放宽断言）。
4. **判定**：PASS / REJECT（列缺陷）/ RETEST（证据不足）——两者由主会话立即回派修复或重测，闭环前**不得向用户宣告该项完成**。
5. **报告**：`test-reports/uNNN-audit-*.md` + 主会话总评表（判定+缺陷计数）呈报用户。
6. **与原审计的关系（合并规则）**：原「审计代理」= 令级审计，已降为高风险令可选；验收审计为每批必做超集（增证据可信度核验+自跑复测+判定协议）；既有审计实践（U68/LGAA/W12b2/U46/W9a-W9b）语义归入本体系，不另设平行环节。

## 3i. 主会话决策权（2026-11-16 用户指令）

1. **自主决策**：非关键矛盾（技术实现取舍、文案、内部接口、测试策略、优先级排序、P2/P3 处置）由主会话直接决策并执行，**不得挂起等人工**；决策记录写入台账/文档。
2. **仍须用户确认（关键项）**：产品语义/交互形态变更、破坏性操作策略、安全策略放宽、用户可见的重要取舍、发布到真实环境的时点（默认允许测试环境）。
3. **待确认提醒**：每轮（cron 汇报）必须列「待您确认」清单及建议——不得静默堆积；清单维护于台账顶部的「待用户确认」节。

## 3h. 业务链路与探索性测试强制门（2026-11-16 用户指令）

1. **验收前置（强制）**：任何验收批开始前必须具备——①按模块的**现状文档**（`current-state/mXX-*.md`，七要素模板）；②**业务链路图**（`current-state/business-flows.md`：入口→步骤→失败分支→模块/API→已有测试）。二者对应当前 HEAD，不得以设计稿/原型替代。
2. **探索性测试为必经环节**：以模块文档与链路图为输入逐链路探索、逐模块操作清单核对；路径清单入库复用；发现→台账→**转化为正式用例**。未执行探索不得宣告完成。
3. **用例基线**：用例必须可追溯来源（模块操作条目/链路步骤/AC）；失败分支与已知缺陷必须有对应用例；覆盖核对按模块文档逐条勾选，未覆盖显式裁定。
4. **闭环**：模块文档/链路图随每次修复更新基线提交；验收审计（§3g）按此基线核对证据完整性。

## 4. 任务多时的拆分

- 单轮并发 ≤4 个子代理（域不相交）；超出部分排队下一轮。
- 通道内串行（同一组件域同一时间只有一个代理）；通道间并行。
- 大任务拆到「单代理 15 分钟可完成」粒度；跨域耦合以已提交契约为界。

## 5. 回收与核验

1. 完成通知到达 → 核验四件：提交内容归属（`git show --stat` 逐文件对照工作令）、测试输出数字、证据目录齐备、与规格无偏差。
2. 审计/测试发现问题 → 回派实现代理修复 → 独立复验 → 三方齐备才关闭令、放行下一个。
3. 失败必须如实入 PROGRESS 与 defect-ledger（🔴→🟡→🟢 状态机），不为绿而改判定。
4. **人工复核反馈回路（2026-11-15 复盘固化）**：宣告「全部完成」后的人工复核反馈（含不通过）触发**证据链升级重验**——按路径清单重放+**每个功能步骤截图**（留盘不提交）；自动化断言「功能可用」≠人工认可「证据可核验」，验收材料双维度交付。
